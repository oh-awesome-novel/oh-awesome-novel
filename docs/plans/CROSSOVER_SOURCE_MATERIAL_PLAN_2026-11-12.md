# 综漫多来源素材规划

> 日期：2026-11-12
> 状态：已立项。作者于 2026-11-12 从四个候选方向中选定本方向，拆为 [1530](../tasks/1530.md)–[1570](../tasks/1570.md) 五个 Planned task。全部尚未实现，实施计划待写。
> 依据：[PROJECT_VISION](../PROJECT_VISION.md)、[2026-11-06 功能路线图](NEXT_FEATURE_ROADMAP_2026-11-06.md) 候选池、[1410](../tasks/1410.md) 与 [1500](../tasks/1500.md) 的交付记录。

## 1. 结论

定位里的“综漫”目前只在 Play 开局这一步有一等支持：1500 让来源带作品归属、让角色默认互不知情。素材这一侧仍按“一次一部参考作品”工作，三处会在综漫创作中反复碰到：

1. **作品归属没有落在正式文件里。** `originWork` 只存在于 Play 的 Launch Package。开局时的预填来自仍保留的采纳审批记录，记录被清理、角色是手写的、或角色来自 Tavern 卡时，就得每次重新手标。
2. **第二部作品的同名人物只能新建。** 1410 的预检遇到已有角色只提示“将新增文件”，明确不做同名认定与合并。综漫里“两部作品里的同一个人”和“恰好同名的两个人”都很常见，现在都靠作者手改目标路径。
3. **参考作品重新拆解后，已采用的内容不知道来源变了。** 采用预览绑定了材料版本，但 Accept 之后没有任何地方告诉作者“这个角色所依据的条目已经改过”。

本轮立五项：

| Task | 内容 | 优先级 / 规模 |
| --- | --- | --- |
| [1530](../tasks/1530.md) | 作品登记与归属：作品清单成为正式文件，角色与设定带作品归属 | P0 / M |
| [1540](../tasks/1540.md) | 跨作品人物对照与合并采用：预检找出可能的已有人物，作者裁定后合并或另建 | P0 / L |
| [1550](../tasks/1550.md) | 参考材料版本比较与重新采用 | P1 / M |
| [1560](../tasks/1560.md) | 跨作品技法对照（只读） | P2 / S–M |
| [1570](../tasks/1570.md) | EPUB / DOCX / 带文本层 PDF 的参考作品导入 | P2 / M |

1530 是 1540 的前置。1550、1560、1570 互相独立，可按使用反馈调整先后。

## 3. 功能设计

### 3.1 作品登记与归属（1530）

**作者问题。** 我的综漫里有哪几部作品、每个角色出自哪一部，应该写在作品文件里，而不是每次开局重新标一遍。

**方案。**

- 新增一份作者可读的作品清单，每部作品有稳定 id、显示名、可选别名，以及它对应的参考作品 id（可以没有，也可以多份——同一部作品的小说和设定集可以是两份 reference）。
- 角色带可选的作品归属。世界设定的归属写法在实施前对照 FILESYSTEM_SPEC 的 World 格式决定，默认写在对象自身，不做集中的“路径 → 作品”索引（集中索引在文件改名后会失配）。
- 原创人物（作者的穿越者、原创配角）不标归属，或标为原创；两者在开局和体检中都不算“缺失”。
- 从已绑定作品的 reference 采用并新建角色时，候选里直接带上归属，作者在 diff 中能看到。
- Play 开局的归属预填改为先读正式归属，没有时再回退到 1500 现有的采纳记录。
- 项目体检增加一条非阻断提示：有两部以上作品时，哪些角色还没有归属。

**边界。** 作品清单与归属是正式文件，创建和修改都走 PendingAction。宿主只检查结构（id 唯一、引用的作品存在），不判断某个角色“实际上”属于哪部作品。没有作品清单的工作区行为与现在一致。

### 3.2 跨作品人物对照与合并采用（1540）

**作者问题。** 从第二部作品采用人物时，系统应该告诉我“这个名字你已经有了”，让我决定是同一个人还是另一个人。

**方案。**

- 预检增加“可能是已有人物”一类说明。匹配是确定性的：来料人物名与已有角色的显示名、别名在规范化（Unicode 兼容归一、大小写、首尾与连续空白）后完全相等才算命中。不做模糊匹配，不调用模型判断同一性。
- 每个命中由作者三选一：
  - **同一人物**：目标改为已有角色目录，生成对已有文件的修改或新增文件；
  - **不同人物**：另建角色，建议的 id 带作品后缀以免混淆；
  - **本次不处理**：从这一批移出。
- 没有命中时作者也可以手动指定“这是已有的某个角色”（来料用了译名或称号时）。
- 裁定前提供只读对照：已有角色的现有文件与来料条目并排。
- 作者的裁定作为“人物对应”记在角色自身的正式文件里（哪部 reference 的哪个人物对应这个角色），随同一次采用的候选一起审批。下次从同一 reference 采用时，预检直接用它给出默认目标。
- 关系材料中的“对方人物”按同一套对应解析为角色 id；解析不了的逐条列为未解决，由作者指定或移出，不猜。

**边界。** 每次生成仍只消费一份 reference；综漫素材依次采用。合并只是既有采用链路上的 update 候选，不新增写入路径，不自动消解设定冲突——两部作品对同一人物说法不一时，两边内容都进候选，由作者在 diff 中取舍。材料条目标识在重新拆解后是否稳定需在实施前核对；不稳定时人物对应以人物名为准，并在材料变更后要求重新确认。

### 3.3 参考材料版本比较与重新采用（1550）

**作者问题。** 我重新拆了一遍原作（或补了后半部），想知道材料改了什么、哪些已经采用的角色和设定需要跟着看一眼。

**方案。**

- 对同一份 reference 的两次已发布材料做条目级比较：新增、删除、内容变化。版本来源是 Git 历史中的已发布材料；工作区没有提交历史或中间版本未提交时，显示“无法比较”及原因，不伪造结论。
- 把变化的条目与采用记录对上：列出“采用过、且来源条目此后变了”的正式对象。采用记录缺失时归为“证据不足”，不说成“未受影响”。
- 每个受影响对象提供两个显式入口：打开文件；带着这些条目进入 1410 工作台重新采用（预填选择与原目标）。
- 回滚：把已发布材料恢复到所选历史版本的内容，由确定性 producer 生成候选，照常预览和 Accept。

**边界。** 比较默认不调用模型。不自动重新采用，不因为材料变了就改动正式角色或设定。Git 与已 Accept 的材料是唯一权威，不另建版本库。回滚只作用于参考材料本身，不连带撤销由它采用出去的正式内容。

### 3.4 跨作品技法对照（1560）

**作者问题。** 我想把两三部作品的写法放在一起看，决定这一章借谁的节奏、谁的对白处理。

**方案。** 选择两到三份已发布且启用的 reference，按蒸馏类别（文风、节奏、钩子、场景技法、人物技法、不可照搬）并排显示条目。作者可以勾选条目，加入本次写作的参考选择；这一步复用现有参考上下文选择器，受同样的预算与使用许可（`allowedUsage`）约束。

**边界。** 只读，不调用模型，不生成“综合文风”，不写任何文件。“让模型总结差异”如果以后需要，作为显式的单次调用另行决定。长期保存的作者文风档案属于候选池里的另一个方向，不在这里引入。

### 3.5 EPUB / DOCX / PDF 参考作品导入（1570）

**作者问题。** 手头的原作常常是 EPUB，现在得先自己转成 TXT。

**方案。** 导入前增加本地格式转换：EPUB、DOCX 首版支持，带文本层的 PDF 作为第二步。转换结果是纯文本加章节边界提示，之后进入现有导入与结构识别流程。原始文件按现有方式保留并记录校验值；来源清单增加转换器标识与版本，使同一文件、同一转换器得到同样的文本。

**边界。** 不联网、不做 OCR、不处理 DRM；扫描版 PDF 与加密文件明确拒绝并说明原因。解压体积、文件数与单文件大小有上限。不执行文档内的脚本或宏，不解析外部引用。新依赖固定版本并随桌面包分发，许可信息进入现有 notices。图片、脚注与排版不保留；章节识别置信度低时沿用现有提示。本任务不扩展导出格式。

## 4. 顺序与依赖

```text
1530 作品登记与归属
  └─ 1540 跨作品人物对照与合并采用

1550 版本比较与重新采用   （依赖 1410 的采用记录；可独立于 1530）
1560 跨作品技法对照       （独立）
1570 多格式导入           （独立）
```

建议先做 1530、1540。1410 仍是 Needs Review（缺完整 Desktop 旅程与部分预检场景的测试）；1540 在同一个工作台上扩展，开工前先把 1410 的旅程测试补上，否则新旧问题会混在一起。

## 5. 不做的事

- 跨 reference 的自动合并、模型判定人物同一性、自动消解设定冲突。
- 一次生成同时消费多份 reference。
- 新的材料数据库、作品版本库或集中的归属索引。
- 多作品时间线自动对齐、自动生成“融合世界观”。长期保存的融合设定仍由作者写成 `world/` 文件。
- 联网抓书、OCR、DRM 处理、更多导出格式。
- 作者文风档案、Play 演出协议与剧本导入、Needs Review 清理——这些是本次未选的方向，仍在候选池。

## 6. 共同约束

- 正式文件只经 CandidateChangeSet → PendingAction → 作者 Accept → ChangeMaterializer → Git 写入。新增的正式文件类型必须先有完整的 final validator，否则保持只读。
- 新增或扩展正式文件格式前先更新 [FILESYSTEM_SPEC](../FILESYSTEM_SPEC.md)；涉及 Launch Package 预填行为的变更同步 [PLAY_MODE_SPEC](../PLAY_MODE_SPEC.md)。
- 预检、对照、版本比较都是确定性的，默认零模型调用；未选条目与未选 reference 的原文不进入任何模型请求。
- 没有作品清单、只用一部参考作品的工作区，行为、存储与请求保持不变，并有回归证明。
- 每个 task 覆盖 Core / Backend / Client / Desktop 的实际入口并有一条走真实后端的作者旅程；测试放在根目录 `__test__/<module>`。受控模型只证明协议与接线，文学质量由作者用真实模型另行验收。

| 问题 | 默认 |
| --- | --- |
