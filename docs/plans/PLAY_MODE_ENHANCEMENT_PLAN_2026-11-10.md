## 1. 结论

Play 的底座已经成立：回合事务、世界事件、分支与存档点、角色认知边界、长局阶段整理、视觉小说演出、结果回流都有生产实现。继续扩建通用基础设施的收益很低。

下一步应该补的是定位里写了、产品里还没有一等支持的两件事：

- **“改写原作剧情”**：Play 不知道原作接下来会发生什么，也不记录作者改掉了什么。
- **“综漫”**：多部作品的来源混在一起，没有作品归属，角色认知和规则冲突全靠模型临场发挥。

另有一批日常使用中的摩擦点，改动小、见效快，建议先做。

## 3. 改进建议

### I1 带要求的重演与补充行动建议

**问题。** 对一回合不满意时，现在只能原样重演碰运气，或恢复存档点后改写行动。作者真正想说的往往是“行动不变，但别让她这么快妥协”。

**设计。**

- 重演确认框增加可选的“这次希望有什么不同”，上限 500 字。行动文本与类型仍从原 artifact 读取，调用方不能覆盖。
- 指引只作用于这一次重演，作为作者层要求进入本轮消息尾部，不进入冻结前缀，不延续到后续回合。
- 新回合仍是同一父节点下的 sibling，旧结果保留。
- “再给几个行动建议”是一次只读调用，复用现有的会话内提问通道（`play-context-question.ts`）。结果只在界面上临时显示，点击后填入输入框，不写入会话快照，不推进 revision。

**需要决定的合同问题。** 重演指引记在哪里：

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| A | 只写入消息日志 | 不改 schema；但消息日志不进 Git，删掉后这条分支为什么不同就无法解释 |
| B（建议） | turn artifact 增加可选的作者视角字段 | 分支可自解释；需要给 artifact 加一个可选字段，并确认读取器对旧 artifact 的兼容规则 |

指引属于 Director 信息，Player 视角的存档点摘要和世界线预览不显示它。

**验收。** 首回合、祖先节点、带到期计划事件的回合都能带指引重演；取消或失败零写入；指引不出现在下一回合的请求里；Player 视角看不到指引。

### I2 采纳表单去 JSON

**问题。** “Bring to writing” 让作者直接编辑 JSON 对象，格式错了只能看报错重来。

**设计。** 四个目标各有一张表单，生成与现在相同的 payload：

| 目标 | 表单字段 |
| --- | --- |
| 章节草稿 | 标题、正文文本框、目标章节（宿主推导，只读展示） |
| 状态 | 对象、字段、新值，可增删多行 |
| 时间线 | 世界内时间、事件、参与者、地点 |
| 伏笔 | 伏笔描述、埋设位置、预期回收条件 |

表单保留“查看 JSON”的只读展开，供排查用。校验错误定位到具体字段。预览、PendingAction、Accept 的链路不变，这是纯界面改动。

**验收。** 四个目标都能不接触 JSON 完成“填写 → 预览 diff → 创建 PendingAction”；表单产出的 payload 与现有后端校验逐字段一致。

### I3 Play 界面中文作者语言

**设计。** 把 Play 的按钮、标签、空状态和错误提示统一为中文，并固定一张术语表，界面、用户文档和提示语共用：

| 现有 | 统一为 |
| --- | --- |
| Immersive Journey / Scene Rehearsal | 沉浸推演 / 场景试演 |
| Quick Start / Guided Start | 快速开局 / 引导开局 |
| Say / Look / Move / Do / Wait | 说 / 看 / 走 / 做 / 等 |
| Act / Advance | 行动 / 推进时间 |
| Checkpoint / Restore / Retry | 存档点 / 回到这里 / 重演 |
| Observation / Outcome Report | 观察笔记 / 结果报告 |
| Bring to writing | 带回写作 |
| Player / Director | 参与者视角 / 导演视角 |

协议字段名、文件名与日志中的英文标识不变。用户文档中三处“截图待补”在这一项里一并补齐。

### I4 用旧开局再开一局

**问题。** 想换一个身份或换一个入场点重新进同一个世界，现在要把向导从头填一遍。

**设计。** 会话列表与会话详情提供“以此开局再开一局”。宿主读取该会话冻结的 Launch Package 或快速开局表单，预填向导，然后**按当前文件重新校验来源**：内容变了的来源标出差异，由作者决定沿用新内容或移除。确认后创建全新会话，与旧会话没有分支关系。

首版不做模板库。同一世界多次开局的需求先由这个入口承接，确实不够用再考虑保存具名开局。

**验收。** 预填后不经修改即可创建；来源缺失或变更时在创建前给出诊断；新旧会话互不影响。

### I5 关系与态度面板

**问题。** 长局里人物关系会多次变化，但这些变化散落在事件流里，回头找“她是哪一回合开始不信任我的”很费劲。

**设计。** 新增一个只读面板，从当前选中分支的 `relationshipChanged` 事件与 `relationship` 类 Pressure 派生：

- 按人物对列出关系变化的时间顺序，每条链接到对应的事件卡片与回合。
- Player 视角只显示可见事件；隐藏原因按现有可见性规则处理。
- 这是可重建的投影，不新增事实文件，不引入好感度数值。纯文学场景不被数值条绑架。

**验收。** 切换分支后面板只反映当前选中路径；Player 视角有隐藏事件不泄漏的反例测试。

## 4. 新功能设计

### N1 原作节点表与偏离账本

**作者问题。** 穿越的乐趣在于“我知道原作接下来会发生什么，然后去改它”。现在裁判把原作时间线当普通背景读，不知道哪些事件还没发生；作者也看不到自己到底改掉了什么、哪些原作事件因此不再成立。

**体验。**

1. 引导开局的入场步骤增加“原作节点”：从已选的 `timeline` 来源中勾选入场点之后的事件，上限 24 条。每条节点冻结来源路径、内容哈希和逐字引文。
2. 选择穿越者是否知道原作。知道时节点对参与者可见，不知道时只有导演视角可见。
3. 推演中，世界 HUD 新增“原作走向”面板，按状态分组：

   | 状态 | 含义 |
   | --- | --- |
   | 待发生 | 原作里会发生，本局尚未触及 |
   | 照常发生 | 本局中按原作发生了 |
   | 已改写 | 发生了，但过程或结果与原作不同 |
   | 已阻止 | 因本局的行动没有发生 |
   | 不再适用 | 前提已不存在，无从谈起 |

4. 每条状态变化都链接到造成它的回合与事件。
5. 结果报告新增“与原作的差异”分组，可作为写作参考或采纳素材带回 Writing，也是 1420 转写章节时最有价值的输入。

**数据模型。**

```ts
type PlayCanonBeatStatus =
  | 'pending'
  | 'occurredAsCanon'
  | 'altered'
  | 'prevented'
  | 'obsolete';

interface PlayCanonBeat {
  id: string;                    // 宿主分配
  label: string;
  source: { sourceId: string; path: string; contentHash: string; quote: string };
  expectedWhen?: string;         // 自然语言，仅作说明
  status: PlayCanonBeatStatus;
  visibility: PlayEventVisibility;
  changedAtTurnId?: string;
  causeEventIds: string[];
  note?: string;
}
```

节点表存放在 Play-local state 的固定键下，做法与 `worldMomentum` 相同。这样它自动随分支快照保存，Restore、Retry 和阶段归档不需要另写一套逻辑。

**运行时。**

- 裁判在回合结算里通过新增的 `canonBeatChanges` 提出状态变化，每条必须带理由，并引用本回合的事件。宿主校验：节点存在、状态迁移合法（终态不能回到待发生）、引用的事件属于本回合。不合法则整回合失败，与现有结算一致。
- 宿主不判断自然语言剧情“算不算发生”。判断由裁判提出，作者在导演视角可以手动更正，更正作为 `manual` 来源的变更记录在案。
- 待发生的节点可以由作者一键转成计划事件，使用现有的触发类型。绝对时间仍须是带时区的 ISO 格式，宿主不猜测自然语言时间。
- 节点被阻止后，裁判可以提出新的 Pressure 作为连锁后果，受现有事件预算约束。宿主不自动生成后果。

**边界。**

- 节点表属于会话，不修改 `timeline/` 正式文件。
- 不做自动推进原作剧情的引擎：没有被转成计划事件的节点不会自己发生。
- 来源文件后来变化时走现有的来源漂移流程，节点保留冻结时的引文。
- 首版只支持沉浸推演（v4）；场景试演是否需要节点表，等实际使用后决定。

**新模块。** `play-canon-beats.ts`（类型、编解码、迁移校验、纯函数的状态迁移）。按 [PLAY_MODE_SPEC](../PLAY_MODE_SPEC.md) 的模块约定独立成深模块，不继续堆进 `play-session.ts`。

**需要在实施计划里确认。** 结算协议增加字段后，旧会话的冻结前缀不含该协议说明：旧会话不启用节点表，只有新建会话可用。是否需要 session schema 或 watermark 变更，要对照现有 v4 严格读取规则核实后再定。

**验收。**

- 新建会话选择节点后，五种状态都能通过真实回合到达，并在 HUD 与结果报告中体现。
- 非法迁移、伪造节点 id、引用非本回合事件都使回合失败且零写入。
- Restore / Retry 后节点表回到对应分支的状态；归档开启新阶段后节点表完整带入。
- 穿越者不知道原作时，Player 视角的 HUD、建议行动和采纳表单都看不到节点内容。

### N2 世界线比较

**作者问题。** 同一个节点试了两种走法，想知道哪条更值得写成正文。现在只能来回切换分支，凭记忆对比。

**设计。** 在世界线视图中选择两个节点，宿主找到共同祖先，并排展示分开之后的差异：

| 维度 | 内容 |
| --- | --- |
| 回合 | 各自的回合数与作者行动列表 |
| 世界时钟 | 各自经过的时间 |
| 状态 | Play-local state 中不同的叶路径与两边的值 |
| 事件 | 只在一边发生的事件 |
| 计划 | 各自待发生、已发生、已取消的计划事件 |
| 认知 | 各自多出的认知与揭示 |
| 原作走向 | 节点状态的差异（依赖 N1） |

比较结果完全由宿主从两条路径的快照确定性计算，不调用模型，不写入任何文件。Player 视角按可见性过滤。面板提供三个出口：切换到某一边、给某一边命名存档点、对某一边生成结果报告。

“用一段话总结两条线的区别”可以作为后续的显式模型调用，不在首版范围。

**验收。** 首回合就分开的两条线、祖孙关系的两个节点、跨越旧版 artifact 的路径都有明确结果或明确的“无法比较”说明；比较不改变当前选中分支与 revision。

### N3 综漫融合契约

**作者问题。** 综漫开局时把两部作品的角色卡和设定一起勾上，结果 A 作品的角色对 B 作品的秘密张口就来，两套力量体系谁压谁每回合都不一样。

**设计。**

1. **来源带作品归属。** 引导开局的来源步骤里，每个来源可以标注所属作品。来自拆书材料采纳的文件可以用采纳记录预填，作者确认后生效。Launch Package 的来源记录增加 `originWork`。

2. **融合契约。** 选择了两部以上作品时，向导增加一步：

   ```yaml
   crossover:
     works:
       - { id: work-a, title: 作品甲 }
       - { id: work-b, title: 作品乙 }
     fusion: merged          # merged 世界融合 | visitor 单向来客 | layered 并存叠层
     knowledge: isolated     # isolated 各作品角色互不知情 | shared 默认互知
     rulePrecedence:
       - topic: 力量体系
         winner: work-a
         note: 乙作的异能在甲作世界被压制到三成
   ```

   契约冻结在 Launch Package 中，进入会话的冻结前缀。

3. **认知隔离。** `knowledge: isolated` 时，每个角色的初始认知边界只包含本作品的来源。场景试演里直接体现在角色的感知包中；沉浸推演里作为带类型的边界交给裁判，并复用现有的分支内认知存储。角色得知另一部作品的信息，必须是一次显式的认知变更，有来源回合，可以追溯。

4. **诊断。** 开局预览增加两类提示：综漫会话里有来源未标注作品；两部作品都提供了世界规则来源但没有任何裁定条目。两者都是警告，不阻断创建。宿主只检查结构，不判断设定在语义上是否冲突。

5. **上下文追踪** 按作品分组显示本轮实际使用的来源。

**边界。**

- 不自动合并同名角色，不自动认定“这两个人是同一个人”。
- 契约只属于会话。作者想长期保存的融合设定，照常写成 `world/` 下的正式文件并在开局时选中。
- 认知隔离是初始边界加可追溯的变更，不保证模型绝不在叙述里说漏嘴，这与现有隐藏信息保护的边界相同。

**验收。** 两部作品各两名角色的合成工作区：隔离模式下角色的感知包不含另一作品来源；跨作品认知只能通过显式变更出现并带来源回合；单作品会话的行为和存储与现在完全一致。

### N4 角色贴合度检查

**作者问题。** 同人最怕写崩角色。沉浸推演里一个裁判扮演所有角色，局越长声线越容易趋同。作者读着觉得不对，却要自己翻角色卡找依据。

**设计。** 作者在一个已提交的回合或一个试演步骤上点击“检查角色贴合度”，这是一次显式的只读模型调用：

- 宿主构造固定的只读材料：该回合的叙述，以及出场名册角色在会话中冻结的角色来源（角色卡事实、互动样例、名册档案）。
- 模型返回若干条意见，每条包含：角色、叙述中的原句、类别（声线 / 动机 / 认知 / 关系）、角色资料中的依据原句、说明。
- 宿主逐条核对：原句必须能在该回合叙述里逐字找到，依据必须能在冻结来源里逐字找到。核对不过的意见丢弃，并显示丢弃数量。
- 结果是建议，不打分，不阻断任何操作。

每条意见提供两个出口：带着这条意见重演（进入 I1 的指引框，作者可以改写）；记为观察笔记。

检查报告保存在会话侧，绑定回合与分支，分支变化后标为过期。它不进入 turn artifact，不参与采纳，不进 Git。

**与已有能力的分工。**

| 能力 | 检查什么 | 性质 |
| --- | --- | --- |
| 认知边界 | 角色不该知道的事 | 宿主强制 |
| Novel LINT | 套话与 AI 味 | 正则规则，面向正文 |
| 贴合度检查 | 声线、动机是否像这个角色 | 模型意见加宿主引文核对，仅供参考 |

**验收。** 没有角色来源的临时角色明确显示“无可对照资料”而不是“没有问题”；伪造引文的意见被丢弃；取消或失败不留下半份报告；Player 视角发起检查时材料不包含隐藏内容。

### N5 回合候选项

> 2026-11-10 追加，来自作者的直接需求。

**作者问题。** 希望每个回合像 GalGame 一样给出多个候选项，可以直接选，可以改了再选，也可以输入全新的选择。

**现状。** 数据通路已经有了：结算里的 `suggestedActions` 最多保存 6 条，随分支快照走。但它没有被当成一等体验：

| 环节 | 现在 | 问题 |
| --- | --- | --- |
| 裁判协议 | 只在字段清单里列出字段名 | 没有数量和差异要求，经常为空或几条雷同 |
| 文本工作台 | 输入框上方的小标签，点击填入输入框 | 不能一键选择，存在感弱 |
| 视觉小说演出 | 最后一拍显示选项，点击即提交 | 不能修改，也不能在演出内自己写 |
| 行动类型 | 界面用前缀正则猜 | 猜不中一律当作“做” |
| 隐藏结算回合 | 候选项被清空 | 这一回合没有任何选项 |

**设计。**

1. **每回合都有像样的候选项。** 在每回合的消息尾部加入规则：给出 3–4 条，站在参与者立场，彼此在做法或态度上明显不同，只写尝试不预设结果，不含参与者不知道的信息。规则放在尾部而不是冻结前缀，已有会话直接生效，前缀缓存不受影响。
2. **不足时不让回合失败。** 候选项少于 2 条或为隐藏结算时，回合照常提交，界面提供“生成候选项”，复用 I1 的只读补充建议。
3. **三种用法在两个视图里都可用。** 直接选（点击或数字键，立即提交）、改一改（放进输入框修改后提交）、自己写（列表末尾固定一项）。视觉小说演出的选项浮层补上后两种，不必返回工作台。
4. **行动类型不再靠猜。** 第一步用固定的类型前缀约定，由宿主确定性解析；第二步再考虑把候选项升级为带类型和态度标签的结构化字段，那需要新增 artifact 字段，单独决定。

**边界。** 候选项只是输入辅助，提交的仍是普通作者行动，走现有回合事务。不做好感度、选项解锁条件或预设的分支剧本树；候选项每回合由裁判根据当前局面给出。首版只覆盖沉浸推演。

**验收。** 见 [1520](../tasks/1520.md)。

## 6. 不做的事

| 不做 | 原因 |
| --- | --- |
| 骰子、属性、技能判定系统 | 会把推演变成数值游戏；现有 Pressure 的 `level` 已是可选项 |
| 每个角色一个独立 Agent | 与 ADR 0002 冲突；场景试演已用单裁判加逐角色感知包达到效果 |
| 后台自动推进原作剧情或自动续局 | 世界只在显式回合中结算，这是现有合同 |
| 生图、TTS | 延续 1360 的范围决定 |
| 把节点表、契约、检查报告做成正式小说事实 | 它们属于会话；进入正式文件只有显式采纳一条路 |
| 开局模板库、公共角色卡或剧本市场 | 个人工具不需要；I4 先承接复用需求 |

## 7. 共同约束

- Play 的全部新增状态都是 non-canonical。正式文件只经由 CandidateChangeSet → PendingAction → 作者 Accept → ChangeMaterializer → Git 写入。
- 模型只读宿主给出的固定投影，不获得主机文件系统、网络或内部目录的访问权。
- 新增的领域状态建立独立模块，由 `play-session.ts` 组合；包入口保持稳定。
- 只读模型调用（补充建议、贴合度检查）都由作者显式发起，有调用次数上限，失败不影响会话。
- 兄弟分支、未提交的草稿和隐藏内容不得进入 Player 视角的任何新面板。
- 涉及结算协议或 artifact 字段的变更（I1 方案 B、N1、N3），实施前先在 [PLAY_MODE_SPEC](../PLAY_MODE_SPEC.md) 明确合同与旧会话的兼容规则。
