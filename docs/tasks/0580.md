## Goal

在 workspace 工作台中增加 Git 记录查看和操作页面，让作者能看到小说工程的历史、当前未提交变更、同步状态，并能执行明确的 Git 操作。

当前已有最小 GitReviewTab 和 status/log/diff/commit/sync API；继续复核其路径、预览范围和失败反馈，不重建或替换 Git GUI。PendingAction 接受后按配置自动提交，网络同步由作者显式触发。

同时，workspace 顶部 toolbar 需要提供“在外部编辑器中打开工作空间”的入口，让用户可以直接用 VS Code、Zed、WebStorm / JetBrains IDE 等专业编辑器打开当前 workspace root，并使用这些编辑器内置的 Git 管理能力。

实现分两阶段：

- **Phase A / 当前实现目标**：假设用户电脑存在全局 `git` 命令，通过 backend / Electron main 中的 `child_process.execFile('git', args)` 调用 Git。先完成 Git status、diff、log、commit、quick commit 和 PendingAction accept auto commit。
- **Phase B / 暂缓的后续能力**：Electron 应用内嵌 Git 二进制，并让 Git integration 层显式使用 bundled Git binary。当前安装包已可构建和发行，仍使用全局 Git；bundled Git 不是现有打包的前置条件。Phase B 不改变 Human Approval / PendingAction / API 语义，只替换 Git binary 来源。

## Open Source First

实现前必须先调研可复用的轻量级开源方案，并记录结论。

候选方向：

- 轻量 Git history / Git log UI component。
- 可嵌入的 Git diff / history viewer。
- [`simple-git`](https://www.npmjs.com/package/simple-git) / [`steveukx/git-js`](https://github.com/steveukx/git-js)，后续可用于封装 Git 命令调用，并绑定应用内自带 Git 二进制程序。
- `isomorphic-git` 这类 JS Git 操作库，只作为备选调研方向。

已知注意事项：

- `simple-git` 可以作为默认 Git 操作层：`steveukx/git-js` 将其定位为 Node.js 应用中运行 Git 命令的轻量接口。它不提供 GUI，但能以 Node API 方式调用 Git 命令，适合 Electron backend / main process 封装。
- 当前 Phase A 不要求 `simple-git`，可以直接用 `child_process.execFile` 调用用户电脑上的全局 `git` 命令。
- Phase B 应用需要自带 Git 二进制程序，并让 Git integration 层显式使用该 binary，避免依赖用户系统是否已安装 Git。
- `isomorphic-git` 是 JavaScript Git 实现，可在 Node 和浏览器环境读写 Git 仓库，并支持 fetch / push 等操作；它更适合作为 Git 操作库，不是完整 GUI。
- `gitgraph.js` 可绘制 Git 图，但项目已归档且长期未维护，不应作为默认方案，除非后续 fork 或替代项目满足维护性要求。
- Gitea / Forgejo / GitLab 这类 forge 太重，不适合作为内嵌 workspace Git GUI。

如果选择第三方开源项目，必须评估：

- license 是否兼容本项目。
- 是否仍在维护。
- 是否足够轻量，可嵌入 Electron / Vue 工作台。
- 是否允许只打开本地 workspace 仓库。
- 是否不会引入服务端数据库、账号系统或代码托管平台。

## Git Operation Layer

Git 操作层按阶段实现。

### Phase A: Global Git Command Adapter

当前第一版先实现一个轻量 Git adapter，直接调用用户电脑上的全局 `git` 命令。

要求：

- Git adapter 只能在 backend / Electron main / Git integration 层使用。
- Vue frontend 不直接调用 Git，也不直接访问 filesystem。
- 使用 `child_process.execFile('git', args)` 或等价非 shell API，不使用拼接后的 shell 字符串。
- 所有 Git 命令的 working directory 必须锁定到当前 workspace root。
- Git 命令不得接受 frontend 传入的任意 shell 字符串、任意 Git 子命令或任意 executable path。
- 文件参数必须经过 workspace boundary 校验，并使用 `--` 与 options/revisions 分隔。
- Git 操作结果以结构化数据返回 UI。
- 如果全局 Git 命令不可用，UI 应显示 Git 不可用状态，并禁止 commit / sync 操作。
- 如果当前 workspace 不是独立 Git 仓库或没有 HEAD，UI 显示可恢复状态；当前 sandbox/proposal/Accept 需要真实 repository baseline，不能承诺 non-Git Accept。新建流程初始化，导入已有工程不隐式提交。

Phase A 需要封装的 Git 操作：

- availability / version。
- repo root 检查。
- status。
- log。
- show commit / commit diff。
- add touched files。
- commit。
- fetch。
- pull fast-forward only。
- push。

禁止第一版提供：

- 任意 Git passthrough。
- `reset --hard` / `clean` / destructive restore。
- 自动 merge / rebase / conflict resolution。
- branch 管理 UI。

### Phase B: Bundled Git Binary

后续 Electron 打包阶段再把 Git binary 内嵌到应用中。

要求：

- Git integration 层显式解析 bundled Git binary path。
- 调用 Git 时使用 bundled binary path，不依赖 `PATH`。
- 可保留 global Git fallback，但 UI 必须显示 fallback / degraded 状态。
- 可在 Phase B 引入 `simple-git` 包装命令执行和结果解析。
- `simple-git` 只能在 backend / Electron main / Git integration 层使用。
- 即使使用 `simple-git`，也必须绑定 bundled Git binary，不能让 frontend 直接调用 Git。

## External Editor Entry

为了降低内置 Git UI 的复杂度，workspace 顶部 toolbar 需要支持把当前 workspace root 打开到用户已安装的专业编辑器。

第一版支持的目标：

- VS Code。
- Zed。
- WebStorm / JetBrains IDE。

交互要求：

- toolbar 提供一个明确的“外部编辑器”入口，可以是按钮、下拉菜单或命令菜单。
- 用户选择编辑器后，应用打开当前 workspace root，而不是打开单个文件。
- 如果目标编辑器未安装或无法打开，UI 显示可恢复错误，不改变 workspace 状态。
- 如果多个 JetBrains IDE 可用，第一版可以优先支持 WebStorm；后续再扩展为 JetBrains IDE 列表。
- 该入口只负责启动外部编辑器，不在本应用内执行 Git commit、push、pull 等操作。

安全和边界要求：

- Frontend 只能传递结构化 editor id，例如 `vscode`、`zed`、`webstorm`。
- Backend / Electron main 层必须使用 allowlist adapter 打开外部编辑器。
- 不接受 frontend 传入任意可执行文件路径、shell 命令或命令行参数。
- 打开的路径必须是当前 workspace root，且经过 workspace boundary 校验。
- 外部编辑器中的 Git 操作属于用户显式离开本应用后的手动行为，不属于 PendingAction 自动提交流程。
- 本应用仍必须保留 Human Approval、PendingAction diff view 和 Git history 页面；外部编辑器入口不能替代这些内部确认链路。

## PendingAction Auto Commit Configuration

新需求：PendingAction 执行成功后，默认需要自动提交一次 Git，但用户必须可以通过配置关闭该行为。

第一版 workspace 配置：

```yaml
git:
  autoCommitOnAccept: true
```

默认值为 `true`。

流程：

```text
PendingAction accepted
    ↓
materialize immutable candidate
    ↓
git diff visible
    ↓
validate changed files
    ↓
git.autoCommitOnAccept?
    ├─ true: git add touched files → commit → refresh Git history
    └─ false: show dirty state and quick commit button
```

无论是否自动 commit，网络同步都由作者另行显式触发。

Commit message 第一版可使用确定性模板：

```text
chore(novel): apply pending action <short-id>

<PendingAction title>
```

后续可以让 AI 建议 commit message，但不能在没有人类确认 PendingAction 的情况下提交。

当 `git.autoCommitOnAccept` 为 `false` 时：

- PendingAction accept 仍然通过 ChangeMaterializer 写入 immutable candidate。
- 不自动 `git add`。
- 不自动 `git commit`。
- 不触发自动同步。
- UI 必须展示当前 dirty 状态。
- UI 必须提供“Commit now”快捷按钮，让用户在任何想提交的时候提交。

快捷提交要求：

- 可以放在 workspace toolbar、Git 页面、PendingAction accept 成功后的状态提示中。
- 点击后展示将提交的 dirty files 和 diff。
- 用户必须能确认或编辑 commit message。
- 提交成功后刷新 Git status / Git history。
- 提交失败时展示错误并保留 dirty 状态。

## PendingAction Diff View

候选内容存为 change engine 的内部 immutable draft。用户 Accept 前，真实目标文件不得被覆盖；UI 只读取公开 PendingAction DTO。

Git 页面或 PendingAction 面板需要提供 diff view，用于比较：

```text
左侧：真实目标文件当前内容
右侧：从 public PendingAction view 渲染的 structured changes 与 diff
```

该 diff view 展示 PendingAction 即将造成的变化，而不是已经写入 Git working tree 后的普通 `git diff`。

Diff view 要求：

- 支持按 PendingAction 查看。
- 支持按 touched file 查看。
- 显示真实目标路径。
- 只显示 public DTO 的 operation/path/hash、diff 与 Git receipt 状态。
- 对新增文件、修改文件、删除文件分别给出清晰状态。
- Accept 前通过 backend public DTO 获取 diff；renderer 不读取内部 draft、artifact 路径或文件系统。
- Reject 后 diff view 应显示该 PendingAction 已废弃或不可用。
- Accept 后 diff view 可以切换为普通 Git diff / commit diff。

这条链路让作者审阅待应用的候选变化，内部存储布局不进入产品 UI。

## Explicit Sync

网络同步必须由作者显式触发；自动提交成功本身不授权 fetch/pull/push。当前只支持已配置 Git remote 的简单同步。

建议策略：

- PendingAction 自动提交成功后只刷新本地状态。
- 应用启动或进入 workspace 后可以读取本地 remote 配置，不自动联网。
- 用户可以手动点击同步。
- 同步失败只展示错误，不回滚已完成的本地 commit。

第一版 sync 能力：

- 显示 remote 名称和当前分支。
- `fetch` / `pull --ff-only` 或等价安全策略。
- `push` 当前分支。
- 失败原因展示。
- 网络不可用、未配置 remote、鉴权失败时可恢复。

- 不绕过 Human Approval：只有 accepted PendingAction 可以触发写入和自动 commit。
- Tool 不直接 commit；commit 应发生在 Human Approval / Git integration 层。
- 不允许自动提交未被 PendingAction touchedFiles 覆盖的文件。
- `git.autoCommitOnAccept: false` 时不得自动提交或自动同步。
- 快捷提交是用户显式 Git 操作，不属于 AI 自主行为。
