## Related Plans

## Goal

把推演结果带回写作时填表单而不是手改 JSON；Play 界面统一使用中文作者语言。

## Existing Baseline

[1170](1170.md) 的采纳链路（证据闭包、预览、PendingAction）完整可用，但表单以 “Editable JSON payload” 表达待采纳数据。Play 界面的按钮与标签多为硬编码英文，例如 `PlayComposer.vue` 的 `Act` / `Advance`。

代码入口：Desktop `PlayAdoptionDraftForm.vue`、`PlayAdoptionPanel.vue`、`usePlayAdoptionPreview.ts` 及 `components/play/` 下各组件；用户文档 `wiki/guide/play.md`。

## Scope

- 章节草稿、状态、时间线、伏笔四个采纳目标各有一张类型化表单，产出与现有后端合同相同的 payload。
- 表单保留只读的“查看 JSON”展开；校验错误定位到具体字段。
- Play 的按钮、标签、空状态与错误提示统一为中文，采用规划文档中的术语表；界面、用户文档与提示语共用同一套说法。
- 更新 `wiki/guide/play.md` 的操作名，并补齐其中三处“截图待补”。

## Constraints

- 纯界面与文档改动：不改采纳 payload 合同、预览、PendingAction 与 Accept 链路。
- 协议字段名、文件名、日志中的英文标识保持不变。
- 不引入新的国际化框架，除非现有界面已有可复用的机制。
- Player 视角的表单仍不得显示隐藏内容或 canonical baseline。

## Done Criteria

- 四个目标都能不接触 JSON 完成“填写 → 预览 diff → 创建 PendingAction”。
- 表单产出的 payload 通过现有后端校验；非法输入在提交前有字段级提示。
- Play 主要旅程（开局、推进回合、历史控制、试演、结果报告、采纳）中不再出现英文操作名。
- 用户文档与界面用词一致，Wiki 构建通过。

## Dependencies And Sources

- 复用 1170；与 [1420](1420.md) 的转写入口共用术语。
- 依据：[PROJECT_VISION](../PROJECT_VISION.md) “新增界面与说明优先使用中文作者语言”。

## Implementation Notes

2026-11-10 交付。

采纳表单：
- `composables/playAdoptionForm.ts` 把四个目标的 payload 与表单互转。表单只改显示的字段，id、来源标记、依据指纹等其余字段原样保留，因此默认建议往返后与服务端 payload 完全相同。校验与后端规则一致（章节编号、YAML 文件安全路径、点路径段、必填与长度），错误定位到字段。
- 章节草稿：标题、正文、写入方式，目标章节只读。状态：文件、对象路径、可增删的“字段 / 新值”行；原值不是字符串时按 JSON 编辑并提示。时间线：世界内时间（`date`）、事件（`summary`）、参与者（`participants` 列表）、地点（`location`）。伏笔：描述（`summary`）、埋设位置（`firstChapter`）、预期回收条件（`expectedResolution`）。键名取自 [FILESYSTEM_SPEC](../FILESYSTEM_SPEC.md) 的示例。
- “查看 JSON”为只读展开，显示将要提交的 payload。

中文作者语言：
- Play 组件、试演、开局、结果报告、上下文检查与消息日志的按钮、标签、空状态和状态提示改为中文，采用规划文档术语表；枚举值（世界活跃度、事件密度、压力类型、动向状态、试演 / 步骤状态、结果标签与置信度、来源状态等）经 `composables/playTerms.ts` 显示。协议字段、文件名和日志标识不变。
- 组合式函数中面向作者的错误、状态与播报改为中文。只在内部不变量被破坏时才会出现的流协议断言（如“stream identity changed”）仍为英文。
- 没有引入国际化框架。

文档：`wiki/guide/play.md` 改用界面上的中文操作名，补上引导开局确认、试演步骤、带回写作表单三张截图（另加带要求重演一张），并重新采集了三张旧的英文界面截图；`wiki/guide/faq.md`、`wiki/screenshots.md` 同步。截图中的叙述来自受控演示模型，已在截图页说明。

实施中发现并修复的既有问题：
- 后端会规范化采纳 payload（章节草稿补标题，时间线补 title / time），客户端却要求返回的 payload 与请求或默认值逐字段相同，导致章节草稿等预览在真实应用中总是被判为无效。客户端改为要求目标与写入位置一致（章节编号与写入方式、文件与路径、状态值），具体字节仍由预览指纹和作者审阅的 diff 约束；表单在预览后载入规范化结果，确认按钮随之可用。payload、预览、PendingAction 与 Accept 的服务端合同没有变化。
- 场景试演舞台的网格行会被压缩，导致步骤区与下方面板重叠；`.play-rehearsal-stage` 改为 `grid-auto-rows: max-content`。

验证：Desktop 表单模型 5 项（四个目标的默认 payload 往返后通过 Core `normalizePlayAdoptionBusinessTarget`，字段级错误）、表单组件测试、客户端规范化 payload 接受 / 改变位置拒绝；全部 Desktop 测试按中文文案更新。浏览器里以时间线表单完成“填写 → 预览 diff → 创建待确认改动”，正式文件未改变。
