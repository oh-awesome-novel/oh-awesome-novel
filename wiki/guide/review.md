# 审阅与接受修改

AI 对小说文件的修改会先形成 PendingAction（待审批修改）。你可以查看新增、修改和删除的文件及差异；只有点击 `Accept` 后，候选内容才会写入真实文件。

聊天回复、拆书预览或 Play 结果中的文字，不等于已保存的小说内容。

## 找到待审批项

点击顶部 `Pending actions`，打开右侧 `Approval`。Copilot 对话中的 `Review` 或 `Open review` 也可以进入审阅。右栏收起时，中央会显示紧凑的审批入口。

每张卡片包含标题、说明、涉及的文件数或路径，以及状态。`Created` / `Updated` / `Deleted` 分别表示新增、修改和删除文件。

[![Approval 审阅面板的空列表状态](/screenshots/approval.jpg)](/screenshots/approval.jpg)

图中尚无待审批修改，因此显示 `No pending actions`。实际产生候选修改后，这里才会出现审批卡片。

## 读懂 Diff

1. 先检查目标路径：是否是你本轮要求修改的章节、角色或记录。
2. 点击 `Diff`，查看完整的文件列表和文本差异。
3. 查看删掉的内容和新增内容，特别留意事实、人物关系、时间点和未要求删除的段落。
4. 多文件修改要逐个检查；一次 `Accept` 会接受该待审批项的整组修改，当前没有逐行勾选接受的入口。

普通文本差异中，以 `-` 开头的行表示移除，以 `+` 开头的行表示新增；`---`、`+++` 和 `@@` 等是差异的定位信息。

右侧 `File` 显示当前实际文件，`Diff` 显示候选改动。接受前在文件预览中看不到新增内容，是正常情况。

[![章节整理候选的 Diff，列出章级状态和章节摘要两个目标文件及差异](/screenshots/review-diff.jpg)](/screenshots/review-diff.jpg)

图中候选使用示例正文的真实引文，通过正式章节整理接口生成；未调用模型，也未点击 Accept。它展示可审阅的实际差异，不表示这些内容已经写入正式文件。

## 审阅整理本章的结果

`/整理本章` 会基于当前选中的正文章节生成同一项审批，目标为该章的 `summaries/chapter/卷号/章号.md` 和 `state/chapters/卷号/章号.yaml`。这是固定范围的章节整理，不要求先把这两个输出文件逐一选为编辑目标。

审阅时分两步核对：

1. **观察记录**：读每条事实、置信度、引文和行号。确认角色身份、发生时间及叙述中的不确定性没有被误解；传闻不能仅因原文提到就变成客观事实。
2. **文件差异**：只有高置信度观察进入摘要和章级状态。查看两个文件的全部增删，尤其是更新已有记录时是否移除了你还需要的内容。

系统校验正文版本、引句和位置。校验通过不等于自动证明事实解释正确，仍由你判断是否接受。中低置信度观察和未解决歧义只出现在报告，不会因此写入正式记录。

一次 `Accept` 会写入这项审批中的全部文件，不支持只接受其中一条观察或一份文件。需调整时先拒绝，再说明应修正的观察并重新整理。

Accept 之前若源章节发生变化，即使这两份输出没有被编辑，旧提案也会失效。此时根据最新正文重新运行 `/整理本章`。整理不会修改正文，也不会自动更新全局状态、时间线、伏笔或人物档案。

详见[整理本章操作步骤](writing.md#整理本章-保存有证据的摘要与状态)。

## 接受或拒绝

### Accept：接受本项全部修改

确认内容后返回 `Approval` 点击 `Accept`。应用会重新检查目标文件、Git 状态以及必要的来源是否仍然匹配，再应用修改。成功后状态为 `accepted`，文件树、章节、待审批列表和健康状态会刷新。

如果开启默认的自动提交，接受后还会尝试为本项修改创建 Git 提交。**文件已接受**和**Git 已提交**是两个结果；完成后到 `Git` 页检查历史。

### Reject：丢弃候选修改

点击 `Reject` 后，该项变成 `rejected`，不会改动目标小说文件。需要调整建议时，可以先拒绝，再明确告诉 Copilot 要保留和要修改的部分，生成新的一项。

已接受的修改不能再通过 `Reject` 撤销。需要恢复内容时，应基于当前文件提出新的修改，或在你熟悉的 Git 工具中审阅后恢复相应内容。

## 提示过期时怎么处理

待审批项生成时会记录当时的文件和 Git 版本。之后发生以下变化，都可能使它失效：

- 你在外部编辑器里改动了目标文件。
- 你接受了另一项修改，或另一个窗口提交了新版本。
- 工作区切换了分支或 Git 最新提交发生变化。
- 参考资料或 Play 分支等来源已经更新。

此时可能看到 `Canonical baseline changed`、`Repository baseline is stale`、`stalePreview` 或同类提示。不要尝试强行接受旧差异。

1. 打开当前文件，确认最新内容。
2. 拒绝已经失效的旧待审批项。
3. 让 Copilot 基于最新文件重新提出修改；Reference 或 Play 的采纳操作则重新生成对应预览。
4. 再次查看新差异后决定是否接受。

如果 Git 中有**与本项无关的已暂存文件**，接受也会被阻止。先处理那些文件的提交或取消暂存，再按提示重试；如果提交使 Git 最新版本改变，需要重新生成候选项。具体操作见 [Git 与历史](git.md)。

## 文件已接受，但 Git 提交失败

在文件成功写入之后，Git 提交仍可能因身份配置、已有未提交修改或其他 Git 错误失败。应用不会为了 Git 失败而自动回滚已经接受的小说文件。

遇到这种情况：

1. 先打开目标文件，确认内容已经存在，避免再次接受同一段修改。
2. 到 `Git` 页查看错误、变更文件和提交历史。
3. 处理错误后，若审批卡片提供 `Quick commit`，可使用它显式重试提交；也可以按 Git 页的说明操作。
4. 确认历史中出现所需提交后，再进行依赖该版本的下一轮编辑。

`git.autoCommitOnAccept: false` 时，接受仍会写入文件，但不会自动提交或同步。左侧底部显示「Git 手动提交」，请显式检查和提交变更。配置方法见 [模型与偏好设置](settings.md#git-自动提交)。

## 中断后先看实际状态

关闭窗口或网络中断后，重新进入工作区，先检查目标文件、`Approval` 和 Git 历史。不要仅依据最后一条聊天消息判断是否成功，也不要手工删除内部审批数据来“重置”结果。

若同一问题持续出现，保留错误文字和涉及的文件路径，按 [常见问题](faq.md) 排查。
